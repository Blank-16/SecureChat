# SecureChat

End-to-end encrypted messaging application. Browser-based X3DH-style key
agreement, a symmetric double-ratchet for 1:1 conversations, and a shared
group master key (GMK) model for groups. Node/Express/WebSocket server,
PostgreSQL persistence, React client.

This document covers architecture, setup, the security model, and a list
of known limitations and production considerations that anyone deploying
or extending this project should read first.

## Architecture overview

```
client (React + Vite)  <-- HTTPS / WSS -->  nginx  <-->  server (Express + ws)  <-->  PostgreSQL
```

- **Transport**: REST for registration/login/session, WebSocket for
  everything that happens after authentication (messages, typing
  indicators, contacts, groups, presence).
- **Encryption boundary**: all message plaintext is encrypted and
  decrypted in the browser. The server only ever stores and relays
  ciphertext — it has no ability to read message content even with full
  database access.
- **Persistence**: PostgreSQL on the server (durable, async, concurrent).
  Key material lives client-side only, in IndexedDB, wrapped with a
  passphrase-derived key (PBKDF2 + AES-GCM).
- **Group encryption**: a single AES-GCM group master key (GMK) is
  generated by the group creator and distributed to each member
  individually, encrypted to that member's public pre-key (ECIES). The
  GMK itself never leaves the browser as raw exportable key material —
  it's generated and held as a non-extractable `CryptoKey` and is only
  ever exported transiently, in memory, at the moment of wrapping it for
  a specific recipient.

## Getting started (local dev)

### Prerequisites

- Node.js 20+
- A running PostgreSQL instance (local install, or `docker run -p
  5432:5432 -e POSTGRES_PASSWORD=changeme -e POSTGRES_USER=securechat -e
  POSTGRES_DB=securechat postgres:16-alpine`)

### Server

```bash
cd server
cp .env.example .env   # edit DATABASE_URL / ALLOWED_ORIGINS as needed
npm install
npm run dev
```

The server validates its environment at boot (see `src/env.ts`) and will
refuse to start with a clear error message if `DATABASE_URL` or
`ALLOWED_ORIGINS` is missing or malformed. On first successful connection
it runs `migrate()`, which creates all tables idempotently — no separate
migration step is required for local development.

### Client

```bash
cd client
cp .env.example .env
npm install
npm run dev
```

Open the printed Vite URL (typically `http://localhost:5173`). Make sure
`ALLOWED_ORIGINS` on the server includes this exact origin, or the
WebSocket connection will be rejected (see Security model, CSWSH
protection).

## Getting started (Docker)

```bash
cp .env.example .env   # set POSTGRES_PASSWORD
docker compose up --build
```

This brings up four services: `postgres` (with a healthcheck gating
startup of dependents), `server` (waits for Postgres to be healthy, runs
migrations on boot, exposes `/healthz`), `client` (static build), and
`nginx` (reverse proxy, waits for the server to report healthy before
accepting traffic). By default the compose file is configured for
`https://localhost` — update `ALLOWED_ORIGINS` and `CLIENT_ORIGIN` and
supply real TLS certificates under `./certs` for any non-local
deployment.

## Environment variables

### Server (`server/.env`)

| Variable | Required | Description |
|---|---|---|
| `PORT` | no (default 4000) | HTTP/WS listen port |
| `DATABASE_URL` | **yes** | PostgreSQL connection string |
| `ALLOWED_ORIGINS` | **yes** | Comma-separated origins allowed for CORS and WebSocket upgrade. In production every entry must be `https://`. |
| `CLIENT_ORIGIN` | no | Falls back to the first entry in `ALLOWED_ORIGINS` |
| `SESSION_TTL_DAYS` | no (default 30) | Session cookie / row lifetime |

|---|---|

| `VITE_WS_URL` | Base URL for the WebSocket connection |

| Variable | Description |
|---|---|
| `POSTGRES_PASSWORD` | Required — compose fails fast if unset |

## Security model

### Identity and authentication

Each user has a long-term ECDSA identity key pair and a signed pre-key
pair, generated client-side. Registration sends only public keys to the
server. Login is challenge-response: the server issues a random nonce,
the client signs it with the identity private key, and the server
verifies the signature against the stored public key. No password ever
touches the network or the server.

The passphrase a user enters is used only to derive (via PBKDF2,
200,000 iterations) a local AES-GCM key that wraps the private key
material before it's written to IndexedDB. The server never sees it.

Session tokens are 256-bit values from `crypto.randomBytes`, and only a
SHA-256 hash of the token is stored server-side — a database compromise
does not yield replayable session tokens directly.

### 1:1 messaging — symmetric ratchet

Initial key agreement follows an X3DH-style exchange using each party's
identity key and pre-key. From the resulting shared secret, HKDF derives
a root key and two chain keys (one per direction). Each message
advances the sending chain one step (`ChainKey_n -> ChainKey_n+1`,
`MessageKey_n` derived from `ChainKey_n`), giving forward secrecy within
a conversation. Every encrypted payload carries a message index so the
receiver's ratchet can detect and correctly handle out-of-order or
dropped messages, caching a bounded window (100) of skipped message keys
for messages that arrive late.

Ratchet keys are derived as **non-extractable** `CryptoKey` objects. They
survive serialization into IndexedDB (the structured clone algorithm
supports `CryptoKey`), but JavaScript — including an XSS payload running
in the page — cannot call `exportKey` on them to read the raw bytes out.

### Group messaging — shared GMK

Groups use a simpler model than the 1:1 ratchet: one AES-GCM group master
key, generated by the creator, distributed to each member via ECIES
(encrypted individually to each member's pre-key). Messages are signed
with the sender's identity key in addition to being encrypted, so
recipients can verify sender authenticity within the group even though
all members share the same symmetric key.

Group membership changes (add/remove member, rotate key) are restricted
to group admins (the creator is admin by default) — a non-admin member
cannot add or remove other members or force a key rotation. The server
also refuses to remove the last remaining admin from a group, since that
would leave the group permanently unmanageable.

### Transport-level protections

- **CSWSH (cross-site WebSocket hijacking) protection**: the server
  validates the `Origin` header on every WebSocket upgrade against
  `ALLOWED_ORIGINS` before accepting the connection or reading the
  session cookie. Without this, any external page could open a
  WebSocket to the server and ride the visitor's authenticated session,
  since browsers attach cookies to WebSocket handshakes automatically
  and (unlike `fetch`) do not apply CORS to them.
- **Content-Security-Policy**: configured via Helmet with no
  `unsafe-inline`/`unsafe-eval`, `frame-ancestors 'none'`, and
  `object-src 'none'`. This is the primary mitigation against the impact
  of an XSS bug, since it blocks the most common script-injection
  vectors outright.
- **Rate limiting**: both REST (`express-rate-limit` on `/auth`) and
  WebSocket (a custom per-connection token bucket) are rate-limited.

### What the server can and cannot see

The server can see: who is messaging whom, when, and how often (traffic
metadata), group membership, and public key material. The server cannot
see: message content, group message content, or any private key
material — these never leave the browser unencrypted (with the single
exception of being held in JS memory transiently while a message is
being encrypted/decrypted, which is unavoidable for any client-side
crypto implementation).

## Known limitations and trade-offs

These are documented deliberately rather than silently shipped — read
this section before relying on this project for anything sensitive.

- **No Signal-style asymmetric Double Ratchet / one-time pre-keys.** The
  1:1 ratchet here is a symmetric chain derived from a single static
  pre-key exchange, not a full Diffie-Hellman ratchet with one-time
  pre-keys. It provides forward secrecy going forward in a conversation
  (compromising a later chain key doesn't expose earlier messages) but
  does not provide the same multi-device / post-compromise security
  properties as the full Signal protocol, and reuses the same pre-key
  for every initiator until the user re-registers.
- **No multi-device support.** Key material is tied to a single
  browser's IndexedDB. Logging in on a second device with the right
  passphrase generates a *new* identity (`unlock()` will fail with "no
  keys on this device" and route the user toward registration) — there
  is no key-syncing or linked-device mechanism.
- **No group post-compromise security.** Because all group members share
  one symmetric key, anyone with that key (including a removed member,
  until the next rotation) could decrypt messages sent before they were
  removed if they retained the key locally. Removing a member rotates
  the key going forward but cannot retroactively protect prior messages
  from someone who already has them.
- **Skipped-message-key window is capped at 100.** If a client misses
  more than 100 consecutive messages in a 1:1 conversation (e.g. offline
  for a very high-volume conversation) before reconnecting, the ratchet
  will refuse to advance further and that conversation's session will
  need to be manually reset.
- **Pagination exists server-side but has no "load more" UI yet.** The
  WebSocket history handlers (`get_history`, `get_group_history`) accept
  an optional `beforeId` cursor and return `hasMore`, but the client
  currently only requests the latest page on load. Wiring up
  infinite-scroll is a frontend task, not a backend limitation.
- **Soft-deleted messages are purged hourly, not instantly.** When a user
  deletes a 1:1 conversation, their copy is marked deleted immediately
  (and excluded from their own history queries immediately) but the row
  itself is only hard-deleted once *both* parties have independently
  deleted it, swept by an hourly background job. This is intentional
  (it's what prevents one party's deletion from destroying the other
  party's copy) but means deleted data can persist in the database for
  up to an hour after both parties have deleted it.
- **No read receipts, message search, file attachments, or disappearing
  messages.** These are common in comparable products but are not
  implemented here.

## Production checklist

Items to verify before exposing this outside a local/dev environment:

- [ ] `NODE_ENV=production` set, and every `ALLOWED_ORIGINS` entry uses
      `https://` (the server enforces this at boot and will refuse to
      start otherwise)
- [ ] Real TLS certificates in place for nginx (`./certs`) — the compose
      file as shipped uses `https://localhost` and is not pre-configured
      with a certificate
- [ ] `POSTGRES_PASSWORD` set to a strong, unique value, not the example
      default
- [ ] `SESSION_TTL_DAYS` reviewed for your threat model
- [ ] Postgres backups configured — there is currently no automated
      backup story in `docker-compose.yml`
- [ ] Log aggregation in place — `console.error` calls throughout the
      server are the only logging mechanism; nothing is shipped to an
      external log sink by default
- [ ] Review the Known limitations section above against your actual use
      case, particularly the lack of multi-device support and group
      post-compromise security

## Project structure

```
server/
  src/
    env.ts              Boot-time environment validation
    app.ts               Express app factory (CORS, CSP, rate limiting, /healthz)
    index.ts              Process entry point: validates env, connects DB, starts HTTP+WS
    db.ts                  All PostgreSQL queries and migrations
    cookies.ts            Session cookie helpers
    wsHandlers.ts        WebSocket connection lifecycle, origin check, message dispatch
    routes/auth.ts        Register / challenge / login / logout / me
    middleware/            CORS, error handling
    ws/
      rateLimit.ts          Per-connection token-bucket rate limiting
      handlers/             chat, group, contacts, auth (per-connection) handlers, shared utils
    types/                 Shared message and DB row type definitions

client/
  src/
    utils/crypto/
      keys.ts                Identity / pre-key generation, signing
      ratchet.ts              Symmetric ratchet: session state, send/receive key derivation
      encryption.ts          High-level encrypt/decrypt for 1:1 and group messages, ECIES, GMK wrap/unwrap
      storage.ts                IndexedDB persistence for wrapped key material
      constants.ts, helpers.ts
    store/                  Zustand stores: auth, crypto, chat, toast
    hooks/                  useEncryption, useChat, useWebSocket
    components/             Auth forms, chat dashboard, safety-number verification modal, etc.

nginx/proxy.conf            Reverse proxy config
docker-compose.yml           Postgres + server + client + nginx
rework.md                      Audit findings and remediation checklist (historical record)
```
